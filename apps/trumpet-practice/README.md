# Practice Stars

Imported from `simonchatts/trumpet-practice` at commit `140a2a5` (18 August 2026). The runtime source and generated assets retained their filesystem modification times during import.

Run this app from the monorepo root with `npm run dev -- trumpet-practice`.

Practice Stars is a colourful daily task tracker for a child. It was built for
tracking trumpet practice, but the task is configurable. The app lets the user
mark each day as:

- **Done**: the task was completed, and a reward picture is unlocked.
- **Good reason**: the task was skipped for a valid reason, and the day does not
  break a streak.
- **Blank**: the task was not completed.

The UI is designed for an iPad in landscape orientation. It has a calendar,
current and best streak counters, a reward image viewer, applause sounds, and
small celebration effects.

**Note**: the app does not work in private browser mode, since it relies on IndexedDB.

## Development Setup

This repository uses Nix for development dependencies.

```bash
direnv allow
npm install
just dev
```

Useful recipes:

```bash
just             # list recipes
just dev         # run the Vite dev server
just check       # ruff, prettier, TypeScript, production build
just format      # format Python, TypeScript, CSS, HTML, JSON, and Markdown
just assets      # regenerate static config and asset manifests
just build       # build dist/
just deploy      # build and deploy to apollo
```

## Configuration

The runtime app reads `public/config.json`, which is generated by
`scripts/generate_asset_manifests.py`.

Current generated config:

```json
{
  "tasks": {
    "trumpet_practice": {
      "name": "trumpet practice",
      "image_version": "trumpet_practice_1"
    }
  },
  "applause_version": "applause_1"
}
```

On first run, the app asks for:

- the user's name
- which configured task to track
- an optional display-name override for that task

That setup state is stored in browser `localStorage`.

## Updating Reward Images

Source reward images live in `kitten-pics/` as `.jpg` files.

To update the current reward set:

1. Add or replace `.jpg` files in `kitten-pics/`.
2. Run `just assets`.
3. Run `just check`.
4. Build and deploy.

The generator copies images to:

```text
public/assets/trumpet_practice_1/images/
```

and writes:

```text
public/assets/trumpet_practice_1/images.json
```

If you want deployed clients to re-download the image set, bump
`IMAGE_VERSION` in `scripts/generate_asset_manifests.py`, then run
`just assets`. Keep old image files available when changing versions if any
existing saved records may still reference them.

## Updating Applause Sounds

Source applause sounds live in `applause/` as `.mp3` files.

To update them:

1. Add or replace `.mp3` files in `applause/`.
2. Run `just assets`.
3. Run `just check`.
4. Build and deploy.

The generator copies sounds to:

```text
public/assets/applause_1/applause/
```

and writes:

```text
public/assets/applause_1/applause.json
```

If deployed clients should re-download applause, bump `APPLAUSE_VERSION` in
`scripts/generate_asset_manifests.py`.

## Adding More Tasks

The app supports multiple tasks in the config format, but the current generator
emits only `trumpet_practice`.

To add more tasks durably, update `scripts/generate_asset_manifests.py` so it
emits additional entries under `tasks`, each with:

- a stable task id, such as `flute_practice`
- a display name, such as `flute practice`
- an image version whose manifest exists under `public/assets/<version>/`

Then run:

```bash
just assets
just check
```

## Browser Storage

The app uses two browser storage layers:

- `localStorage` stores the lightweight tracker state: user, task, start date,
  records, and asset versions.
- IndexedDB stores downloaded image and applause blobs.

This avoids putting large image/audio payloads into `localStorage`, which is
too small and inefficient for the reward asset set.

Clearing browser site data resets the app on that device.

## Cloud Backup

Cloud backup is not implemented yet. The code contains a small placeholder
service in `src/cloudSync.ts` so a future backend can be added without
rewriting the app's state model.

The intended future backup payload is the lightweight tracker state only, not
the cached image or applause blobs.
